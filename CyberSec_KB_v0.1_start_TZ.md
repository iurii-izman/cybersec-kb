# CyberSec Knowledge Base v0.1
## Стартовое техническое задание

**Статус:** Draft / Ready to Implement  
**Назначение:** персональная база знаний по кибербезопасности для систематизации обучения на TryHackMe и дальнейшего развития в pentest / offensive security / defensive security.  
**Основной принцип:** база должна помогать **понимать, находить, применять и повторять знания**, а не превращаться в отдельный проект по обслуживанию заметок.

---

# 1. Цель проекта

Создать простой, устойчивый и расширяемый фундамент персональной базы знаний по кибербезопасности, который позволит:

- фиксировать новые понятия, техники, инструменты и практические лаборатории;
- не привязывать знания к структуре конкретного курса;
- быстро находить нужную информацию спустя месяцы;
- связывать теорию с практическим применением;
- накапливать собственные рабочие наблюдения, команды, ошибки и выводы;
- постепенно формировать личную методологию работы специалиста;
- не допускать дублирования одной и той же информации в десятках конспектов;
- со временем расширять систему без болезненной миграции данных.

База должна одинаково хорошо поддерживать:

- TryHackMe;
- Hack The Box;
- PortSwigger Web Security Academy;
- книги и курсы;
- локальные лаборатории;
- собственные эксперименты;
- дальнейшую профессиональную практику в разрешённых средах.

---

# 2. Главная архитектурная идея

База строится не вокруг уроков TryHackMe и не вокруг списка программ.

Основная модель знаний:

```text
Concept
   ↑
   │
Technique ← Tool
   ↑         ↑
   └── Lab ──┘
```

Используются четыре основных типа заметок:

1. **Concept** — что это такое.
2. **Technique** — какую задачу или действие мы выполняем.
3. **Tool** — чем выполняется техника.
4. **Lab** — где знания были применены практически.

Пример:

```text
[[HTTP Status Codes]]          Concept
          ↑
          │
[[Content Discovery]]          Technique
          ↑
          │
       [[DIRB]]                Tool
          ↑
          │
[[THM - Web Enumeration]]      Lab
```

Ключевой принцип:

> Инструмент — не центр базы знаний.  
> Центр — задача и техника, которую этот инструмент помогает выполнять.

Список может расширяться по мере необходимости.

# 10. Поле `status`

Используется для фиксации стадии освоения.

Допустимые значения:

```text
new
learned
practiced
confident
```

Значения:

### `new`

Встретил впервые.

### `learned`

Разобрался в базовой теории.

### `practiced`

Самостоятельно применил в лаборатории.

### `confident`

Могу объяснить и использовать без постоянной подсказки.

---

# 11. Поле `confidence`

Дополнительная субъективная оценка уверенности.

Шкала:

```text
1 — видел / почти не помню
2 — понимаю с подсказкой
3 — могу повторить
4 — могу использовать самостоятельно
5 — могу уверенно объяснить и выбрать в подходящей ситуации
```

Не требуется постоянно обновлять поле.

Оно используется как ориентир, а не как точная метрика.

# 19. Главный рабочий паттерн: Goal → Action → Evidence

При фиксации практических команд использовать структуру:

```text
GOAL
Что хочу получить?

ACTION
Что делаю?

EVIDENCE
Что получил?

INTERPRETATION
Что означает результат?

NEXT STEP
Что делать дальше?
```

Пример:

```markdown
### Поиск web-content

**Goal:** найти неочевидные ресурсы приложения.

**Action:**

```bash
dirb http://TARGET/
```

**Evidence:**

Обнаружен путь `/admin`.

**Interpretation:**

Ресурс существует и требует дальнейшего анализа.

**Next step:**

Проверить ответ сервера, доступ и механизм авторизации.
```

Команда без контекста не считается полноценной заметкой.

# 20. Technique важнее Tool

В базе должно быть легко отвечать не только на вопрос:

> Как пользоваться DIRB?

Но прежде всего:

> Как выполнить Content Discovery?

Пример центральной Technique:

```markdown
# Content Discovery

## Цель

Обнаружить ресурсы веб-приложения, которые не видны через обычную навигацию.

## Можно искать

- directories;
- files;
- backup files;
- admin panels;
- API endpoints;
- служебные ресурсы.

## Методы

### Passive

- robots.txt;
- sitemap.xml;
- HTML;
- JavaScript;
- документация приложения.

### Active

- dictionary-based discovery;
- fuzzing;
- recursive discovery.

## Инструменты

- [[DIRB]]
- [[DirBuster]]
- [[Gobuster]]
- [[ffuf]]

## Labs

- [[THM - ...]]
```

# 21. Правило работы с командами

Не хранить длинные списки ключей ради полноты.

Плохо:

```text
- параметр A
- параметр B
- параметр C
...
- параметр Z
```

Хорошо:

```markdown
### Определить версии сервисов

```bash
nmap -sV TARGET
```

Использовать, когда открытые порты уже обнаружены и необходимо определить сервисы и их версии.
```

Каждая команда должна иметь контекст.

# 22. Правило для Lab

Lab не должен превращаться в переписанный текст TryHackMe.

В Lab фиксируются:

- что было новым;
- что применялось;
- какие команды использовались;
- что получилось;
- как был интерпретирован результат;
- ошибки;
- выводы;
- ссылки на постоянные знания.

Теория должна постепенно уходить в:

```text
Concept
Technique
Tool
```

# 24. Правило создания новых заметок

Перед созданием новой заметки задать три вопроса:

1. Это действительно отдельная сущность?
2. Не существует ли уже заметка с этим смыслом?
3. Будет ли полезно найти эту информацию независимо от конкретного урока?

Если ответ на третий вопрос — нет, информация может остаться внутри Lab.

# 28. Правило качества заметки Tool

Хорошая Tool-заметка должна позволять спустя 6 месяцев примерно за 30 секунд ответить:

1. Что это?
2. Какую задачу решает?
3. Когда использовать?
4. Как выглядит минимальный синтаксис?
5. Какие параметры действительно важны?
6. Как читать результат?
7. Какие типичные ошибки бывают?
8. Какие альтернативы существуют?
9. Где инструмент уже применялся?

Если заметка этого не позволяет — её нужно улучшить.

---

# 29. Правило качества Technique

Хорошая Technique-заметка должна отвечать:

1. Какова цель техники?
2. Когда она применяется?
3. Какие данные нужны на входе?
4. Какие методы существуют?
5. Какими инструментами можно выполнить задачу?
6. Как интерпретировать результат?
7. Что обычно делать дальше?

---

# 30. Правило качества Lab

Хороший Lab должен показывать не только команды, но ход мышления:

```text
Goal
  ↓
Action
  ↓
Observation
  ↓
Interpretation
  ↓
Decision
```

Именно этот слой со временем должен становиться наиболее ценным.

---

# 31. Безопасность и границы использования

База предназначена для:

- собственного обучения;
- TryHackMe;
- Hack The Box;
- CTF;
- собственных лабораторий;
- систем, на тестирование которых получено явное разрешение.

Практические заметки должны по возможности сохранять контекст применения.

Не следует превращать базу в бесконтекстный набор действий против реальных систем.

# 32. Git

Vault рекомендуется хранить в отдельном Git-репозитории.

Минимальный workflow:

```bash
git add .
git commit -m "Add THM web enumeration notes"
```

Частота:

- после заметного блока работы;
- после нескольких лабораторий;
- перед крупной переработкой структуры.

Не требуется создавать commit после каждой заметки.

---

# 33. Рекомендуемый `.gitignore`

Минимально проверить служебные файлы Obsidian.

Пример:

```gitignore
.obsidian/workspace.json
.obsidian/workspace-mobile.json
.trash/
```

Не следует автоматически исключать всю `.obsidian/`, если необходимо синхронизировать полезные настройки Vault.

# 34. Что нельзя делать на старте

- заносить каждую команду без понимания;
- строить сложный dashboard;
- измерять прогресс десятками метрик;
- создавать отдельные domains как глубокое дерево папок;
- использовать одновременно Properties, folders и tags для одной и той же классификации;
- автоматизировать процесс до того, как он стабилизировался вручную.

# 38. Acceptance Criteria

Архитектура считается пригодной для дальнейшей работы, если после нескольких уроков выполняются условия:

### Навигация

Можно за несколько секунд найти:

- инструмент;
- технику;
- базовое понятие;
- лабораторию, где инструмент использовался.

### Повторное использование

Одна Tool-заметка используется из нескольких Labs без копирования.

### Связность

Из Lab можно перейти:

```text
Lab → Tool → Technique → Concept
```

и обратно через backlinks.

### Простота

Обработка одного обычного урока не превращается в отдельную длительную задачу по ведению базы.

### Масштабируемость

Можно добавить новый тип сущности позже без перестройки текущего Vault.

# 39. Триггеры для перехода к v0.2

Не расширять систему заранее.

Рассматривать новые возможности только при появлении конкретных симптомов.

## Добавить Dataview, если

- заметок стало много;
- ручной Home перестал работать;
- нужны динамические списки;
- появилась потребность автоматически искать `status: new`.

## Добавить Anki, если

- информация хорошо каталогизирована, но плохо удерживается в памяти;
- есть устойчивый набор фактов и вопросов, достойных повторения.

## Добавить Procedures / Playbooks, если

- начинают регулярно повторяться цепочки действий;
- отдельные Technique-заметки уже не отражают полный workflow.

## Добавить OWASP / MITRE mapping, если

- появилась потребность сопоставлять собственные знания с профессиональными framework;
- это реально помогает навигации или подготовке.

## Добавить AI-автоматизацию, если

- ручной workflow уже стабилен;
- понятно, какие именно части можно автоматизировать без ухудшения качества.

# 40. Архитектурные принципы проекта

## Principle 1 — Knowledge before tooling

Сначала понять знание, затем выбирать инструмент.

## Principle 2 — Technique before command

Команда должна быть связана с задачей.

## Principle 3 — Evidence before confidence

Уверенность должна расти после практического применения.

## Principle 4 — Links before duplication

Повторно использовать знание через связи.

## Principle 5 — Simple before automated

Сначала рабочий ручной процесс.

## Principle 6 — Evolve from pain

Расширять архитектуру только из реальной необходимости.

## Principle 7 — Course-independent knowledge

TryHackMe является источником обучения, но не архитектурой собственной базы.

# 42. Финальная формулировка проекта

**CyberSec Knowledge Base v0.1** — это не архив конспектов и не энциклопедия инструментов.

Это персональная система, в которой:

- Concepts объясняют **что существует**;
- Techniques объясняют **что нужно сделать**;
- Tools объясняют **чем и как это сделать**;
- Labs доказывают **где это было применено**.

Главная цель первой версии:

> Построить настолько простой фундамент, чтобы им хотелось пользоваться после каждого урока, и настолько правильный архитектурно, чтобы через год не пришлось начинать заново.
